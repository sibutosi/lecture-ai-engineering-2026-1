- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
　`app/config.py` の `RAG_TOP_K`（ベクトル検索で取得する上位件数）をデフォルト値から `1` に変更し、検索結果を最上位の1ページのみに絞るようにした。
- 比較した質問と、固定した条件（モデル・対象資料など）：
　〇 質問：`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`
　〇 固定条件：モデル `gemini-3.5-flash-lite`、検索方式はベクトル検索（`uv run python -m app.agent --trace "$AIE_QUESTION"`）、対象資料は第1〜3回の本講義資料（全214ページ）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
　〇 変更前（デフォルト）：`search_materials` で複数ページ（`lec02-main-p052`, `p051` 等）を取得し、両ページを根拠に正確に回答、所要時間 `2.88` 秒、入力 `3,027` tokens / 出力 `172` tokens、応答 `2` 回、推定コスト `$0.001338` USD。
　〇 変更後（`RAG_TOP_K = 1`）：`--trace` 上で `search_materials` の返却が `lec02-main-p052` の1件のみに変化し、単一ページからLoRA・QLoRAの要点を正確に回答。所要時間 `2.99` 秒、入力 `1,189` tokens / 出力 `192` tokens、応答 `2` 回、推定コスト `$0.000837` USD
- 改善した例と、残る失敗・制約：
　〇　改善点：1ページに答えが集約されている質問では、不要な周辺スライドをプロンプトに渡さずに済むため、入力トークン数とAPIコストを大きく削減できた。
　〇　残る制約：返却件数を1件に固定しているため、複数ページにまたがる比較や前提説明（p.51のPEFT全体像など）が必要な質問では、1回の検索で情報が欠落するリスクがある。
- 気づき・疑問：
　`RAG_TOP_K` を絞るだけでコスト効率は劇的に良くなる一方、質問の複雑さに応じて取得件数を動的に変えたり、不足時にエージェントが追加検索を判断できる設計（プロンプト工夫やGraph/Treeとの使い分け）が実運用では重要になると分かった。
